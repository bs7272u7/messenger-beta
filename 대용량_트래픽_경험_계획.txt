Cloud Chatting 대용량 트래픽 경험 계획

목표
실제 대규모 사용자를 보유하지 않아도, 가상 부하 테스트를 통해 성능 병목을 찾고 개선한 경험을 포트폴리오로 만든다.

중요 원칙
- "실사용자 1,000명을 처리했다"고 표현하지 않는다.
- "k6/Locust 가상 사용자 기반 부하 테스트"라고 명확히 작성한다.
- 숫자보다 테스트 조건, 문제 원인, 개선 전후 결과를 함께 보여준다.

1단계: 테스트 환경 준비
- 현재 Flask + Socket.IO + PostgreSQL 구조를 기준으로 테스트한다.
- Render 운영 서비스가 아닌 별도 테스트 환경 또는 로컬 Docker 환경에서 먼저 진행한다.
- 테스트 계정과 테스트용 채팅방을 미리 만든다.
- k6 또는 Locust 중 하나를 선택한다.
  추천: HTTP API 중심은 k6, Python으로 시나리오를 만들고 싶다면 Locust.

2단계: 측정할 사용자 시나리오 만들기
- 로그인
- 친구 목록/대화 목록 조회
- 특정 채팅방 메시지 조회
- 메시지 전송
- 읽음 처리
- 이미지 없이 텍스트 메시지 위주로 시작

3단계: 부하를 단계적으로 늘리기
- 1차: 가상 사용자 50명
- 2차: 가상 사용자 100명
- 3차: 가상 사용자 300명
- 4차: 가상 사용자 500명
- 목표: 각 단계에서 오류율과 응답 시간이 급격히 나빠지는 지점을 찾는다.

4단계: 반드시 기록할 지표
- 평균 응답 시간
- p95 응답 시간: 느린 상위 5% 요청의 응답 시간
- 초당 요청 수(RPS)
- HTTP 오류율
- Socket.IO 연결/끊김 수
- 서버 CPU와 메모리 사용량
- PostgreSQL 연결 수와 느린 쿼리

5단계: 예상 병목과 개선 후보
1. 메시지 목록 전체 재렌더링
   - 문제: 메시지 하나가 바뀔 때 전체 채팅창을 다시 그리면 화면과 브라우저 부담이 커진다.
   - 개선: 신규/수정/삭제된 메시지만 부분 업데이트한다.

2. 반복 DB 조회
   - 문제: 친구 목록, 온라인 상태, 대화 목록을 매 요청마다 DB에서 읽으면 대기 시간이 늘어난다.
   - 개선: Redis로 온라인 상태와 자주 조회되는 데이터를 캐시한다.

3. 메시지 조회 쿼리
   - 문제: 메시지가 많아지면 대화방 메시지 조회가 느려질 수 있다.
   - 개선: conversation_id + created_at 또는 id 기준 인덱스를 검토하고, 페이지네이션/무한 스크롤을 적용한다.

4. 링크 미리보기와 이메일 발송
   - 문제: 외부 사이트 또는 이메일 서비스 응답이 느리면 채팅 요청 전체가 지연될 수 있다.
   - 개선: 타임아웃을 두고, 캐시 또는 백그라운드 작업 큐로 분리한다.

5. 이미지/영상 전송
   - 문제: 서버가 파일을 직접 전달하면 메모리·대역폭 부담이 커진다.
   - 개선: Cloudinary 또는 S3 같은 객체 저장소에 직접 업로드하고 CDN URL만 메시지에 저장한다.

6단계: 개선 전후 비교표 작성
예시 형식
항목 | 개선 전 | 개선 후 | 적용 내용
p95 메시지 조회 | 1.8초 | 0.45초 | DB 인덱스와 페이지네이션
오류율 | 4.2% | 0.3% | DB 연결 관리와 요청 제한
화면 갱신 | 전체 렌더링 | 부분 렌더링 | Socket.IO 이벤트별 DOM 갱신

7단계: Java 정식 버전 확장 계획
- Spring Boot로 API 서버 구성
- WebSocket 서버를 일반 REST API와 분리
- Redis: 온라인 상태, 세션, 캐시, 서버 간 이벤트 공유
- Kafka 또는 RabbitMQ: 푸시 알림, 이미지 처리, 로그성 작업 비동기화
- Docker Compose: API 서버 2~3개 + Redis + DB 구성으로 수평 확장 실습
- Nginx/로드밸런서: 여러 서버로 요청 분산

8단계: 포트폴리오에 넣을 문장 예시
"k6 기반 가상 사용자 부하 테스트를 통해 실시간 채팅 API의 병목을 측정했습니다.
메시지 전체 렌더링을 부분 업데이트로 바꾸고, 메시지 조회 쿼리 최적화와 캐시 전략을 적용해
p95 응답 시간과 오류율을 개선했습니다."

완료 기준
- 부하 테스트 스크립트 1개 이상 작성
- 50명, 100명, 300명 이상 테스트 결과 저장
- 병목 1개 이상 개선
- 개선 전후 결과표 및 그래프 작성
- README에 테스트 환경, 조건, 한계, 결과를 정리

주의
- 운영 DB나 실제 사용자 계정에 부하 테스트를 하지 않는다.
- Render 무료/저사양 서비스에 무리한 테스트를 반복하지 않는다.
- 테스트 데이터와 테스트 계정은 운영 데이터와 분리한다.
