클라우드 채팅 프로젝트 로드맵 · 정식 웹 v1 재구축 계획
작성일: 2026.08.23

0. 현재 결정
- 웹 정식 버전은 ‘나중에 출시할 목표’가 아니라 지금부터 만드는 Cloud Chatting v1.0이다.
- 현재 Messenger-Beta는 서비스를 바로 끄지 않는다. 기능 검증, 사용자 피드백 확인, DB 백업을 담당하는 베타 기준선으로 유지한다.
- 새 v1 프로젝트는 베타의 모든 기능을 그대로 복사하지 않는다. 실제로 필요한 핵심 기능과 Cloud Chatting의 정체성만 선별해 안정적으로 재구축한다.
- 우선 기술 방향: Flask + Flask-Login + SQLAlchemy + PostgreSQL + Socket.IO + Tailwind CSS.
- 사진·음성 등 미디어는 Cloudinary를 유지하고, 실시간 채팅은 Flask-SocketIO를 유지한다.
- React/TypeScript와 Java/Spring Boot는 v1 완성 뒤 다음 단계의 학습·확장 목표로 둔다.

1. 가장 먼저 할 일: 데이터와 서비스 보호
목표: Render 무료 PostgreSQL 만료 전에 어떤 선택을 하더라도 데이터가 남게 만든다.

- 2026.09.09 전에 Render PostgreSQL 전체 백업(pg_dump)을 로컬의 안전한 위치에 만든다.
- 백업 파일을 빈 테스트 DB에 복원해 계정, 친구, 채팅, 문의, 신고, 체스 전적 데이터가 실제로 복구되는지 확인한다.
- DATABASE_URL, Cloudinary, Resend, VAPID, 관리자 키 등 비밀값은 Git과 문서에 기록하지 않는다.
- DB 운영 선택지는 ‘Render 유료 유지’와 ‘Neon 이전’을 비교한다.
  · 안정성과 빠른 전환이 우선이면 Render 유료 전환
  · 베타 비용 절감이 우선이면 Neon으로 이전 후 충분히 테스트
- 데이터가 유지된다는 확인 전에는 기존 Render DB를 삭제하거나 새 DB로 덮어쓰지 않는다.

완료 기준
- 날짜가 포함된 백업 파일 1개 이상 보관
- 테스트 복원 성공
- DB 이전/유료 전환 방침 결정

2. 정식 웹 v1의 제품 범위 확정
v1의 목표: ‘예쁘고 기능이 많은 앱’보다 ‘안정적으로 대화할 수 있는 메신저’를 완성한다.

v1 핵심 기능(반드시 포함)
- 회원가입, 이메일 인증, 로그인/로그아웃, 아이디·비밀번호 복구
- 프로필: 사진, 배경사진, 소개글, 공개 범위
- 친구 찾기, 친구 요청, 차단, 친구 목록
- 1:1 채팅, 그룹 채팅, 답장·수정·삭제·공감, 링크 미리보기
- 사진·파일·음성 메시지 전송과 업로드 검증
- 메시지함: 친구 요청, 체스 초대, 시스템 안내를 유형별로 구분
- 알림, 공지사항, 도움말/문의, 이용약관, 개인정보처리방침
- 관리자: 문의·신고·공지·회원 이용 제한 관리
- 반응형 모바일 웹, 한국어 기본 + 다국어 번역 구조

v1에서 후순위로 분리할 기능
- 체스의 고급 온라인 매칭·레이팅·관전·인게임 이모티콘 확장
- 계절/시즌 테마의 대량 추가
- PC 앱, 모바일 앱, 소개 홈페이지의 완성형 버전
- Spring Boot 전면 전환

원칙
- 후순위 기능을 삭제한다는 뜻이 아니라, 메신저 핵심 흐름이 안정된 뒤 별도 업데이트로 추가한다는 뜻이다.

3. v1 설계 원칙
백엔드
- Flask Blueprint로 auth, chat, friends, profile, inbox, support, admin, chess를 분리한다.
- SQLAlchemy 모델과 DB 마이그레이션(Alembic/Flask-Migrate)을 사용한다.
- 로그인/세션은 Flask-Login, 비밀번호는 Argon2 또는 bcrypt, 모든 폼은 CSRF 보호를 적용한다.
- API 응답 형식, 오류 코드, 권한 확인 규칙을 통일한다.
- 업로드 파일은 확장자·MIME·용량을 서버에서 검증하고 Cloudinary 공개 설정을 점검한다.

프론트엔드
- Jinja 템플릿 + Tailwind CSS를 기본으로 사용한다.
- 버튼, 입력칸, 카드, 모달, 배지, 빈 화면, 토스트를 공통 컴포넌트 규칙으로 만든다.
- 디자인 참고용 오픈소스는 MIT/Apache-2.0 등 라이선스를 확인하고, 그대로 복사하지 않고 Cloud Chatting 색상·문구·구성으로 재해석한다.
- 모달은 하나의 상태 관리자만 열고 닫도록 하여 삭제/차단 모달 충돌을 막는다.
- 모든 사용자 화면 문구는 번역 키로 관리하고, 기본 언어는 한국어로 고정한다.

디자인 방향
- 기본: 차분한 블루·클라우드 정체성, 충분한 대비와 여백
- 오피스 모드: 눈부심을 낮춘 어두운 중성 색, 둥근 장식 최소화
- 테마: 채팅방 분위기 기능으로만 제공하고 핵심 조작 요소의 가독성을 해치지 않게 한다.
- 모바일 우선으로 설계한 뒤 PC에서는 3패널(목록/대화/정보)로 자연스럽게 확장한다.

4. 재구축 단계
1단계. 설계와 디자인 시스템
- 화면 목록과 사용자 흐름을 먼저 확정: 로그인 → 친구 → 대화 → 프로필 → 메시지함 → 설정 → 관리자
- 색상, 글꼴 크기, 간격, 버튼 높이, 모달 규칙을 문서화
- PC/모바일 와이어프레임 확정

2단계. 계정·프로필·친구 기반
- 인증, 계정 복구, 프로필, 친구 요청/차단/공개범위 구현
- 권한 테스트와 입력 검증 테스트 추가

3단계. 채팅 핵심
- 대화방/메시지/그룹 모델, Socket.IO 이벤트, 읽음/알림/메시지함 구현
- 긴 메시지, 파일, 링크 미리보기, 오류 상태, 빈 화면을 함께 점검

4단계. 운영 기능
- 문의·신고·공지·관리자 인증·이용 제한 구현
- 개인정보처리방침과 이용약관을 실제 수집 데이터 기준으로 검토

5단계. 체스 모듈 연결
- 메신저 핵심과 분리된 Blueprint/화면으로 연결
- 체스 초대는 메시지함으로 수신
- 체스 기능은 별도 테스트와 성능 점검 뒤 업데이트로 확장

6단계. 데이터 이전·검증
- 베타 DB 백업을 v1 테스트 DB에 복원
- 모델 차이용 이전 스크립트를 작성하고 복원 리허설
- 계정, 메시지 수, 친구 관계, 전적의 개수를 대조

5. 품질 기준(기능 완료 판단 기준)
- 기능마다 ‘정상 흐름 + 실패 흐름 + 모바일 화면’을 확인한다.
- 새 기능은 기존 채팅, 로그인, 관리자 기능을 깨지 않는지 회귀 점검한다.
- Python 문법 검사, JavaScript 문법 검사, 체스 엔진 단위 테스트를 자동 실행한다.
- 배포 전 환경변수 누락, 보안 헤더, CSRF, 파일 권한, 오류 로그를 점검한다.
- 중요 데이터 변경 전 백업·복원 절차를 실행한다.

6. v1 이후의 학습·확장 로드맵
1) TypeScript: 프론트엔드 상태와 API 데이터 구조를 안전하게 관리
2) React/Next.js: 소개 홈페이지, 대시보드, 이후 고도화된 웹 UI
3) Java + Spring Boot: 객체지향, REST API, JPA, Spring Security, WebSocket/STOMP, JUnit
4) Spring Boot 기반 차세대 백엔드: Flask 기능을 한 번에 교체하지 않고 기능 단위로 재구축
5) 모바일 앱: React Native 또는 Flutter 검토
6) PC 앱: Electron 또는 Tauri 검토
7) 운영: Docker, GitHub Actions, Redis, Sentry, 부하 테스트, DB 백업·모니터링

7. 지금 당장 결정할 항목
- Render DB: 유료 유지 또는 Neon 이전
- v1 새 저장소/새 프로젝트 폴더 생성 시점
- v1 첫 화면 설계: 메신저 중심 3패널 구조와 모바일 하단 탭 구성
- v1에 체스를 첫 출시부터 포함할지, 첫 정식 업데이트로 분리할지

중요한 원칙
- 베타에서 검증된 경험은 가져가되, 복잡도와 버그까지 그대로 옮기지 않는다.
- 기능 하나를 추가할 때마다 ‘사용자 흐름, 보안, 모바일, 다국어, 오류 상황’을 함께 확인한다.
- 정식 버전은 빠르게 많은 기능을 넣는 프로젝트가 아니라, 오래 유지·확장할 수 있는 기반을 만드는 프로젝트다.
